<h2 id="timeline">Timeline</h2>

All training ran on one shared RTX 5080; every evaluation ran in MuJoCo, a different physics engine from the
Isaac Lab training simulator.

<h2 id="interface">Policy interface</h2>

The policy is written against what the real robot can provide, so it can be exported to the team's skill server
without changes.

| Item | Specification |
|---|---|
| Control | 50 Hz policy on 200 Hz physics (decimation 4) |
| Action | joint targets = default pose + 0.25 · a for the 20 non-head joints; fixed `walk` PD gains (hips/knees 100, ankles 65, arms 20) |
| Head | separate look-at-ball controller (the policy had to be fine-tuned with it in the loop: the old checkpoint fell 16/16 times when the head started tracking the ball) |
| Actor observations | gyro, projected gravity, joint positions and velocities, last action, ball (x, y) estimate in the heading frame with validity and age, command (direction, range); later + 10 older ball detections (300 ms of history) |
| No privileged state | the actor sees only on-robot signals; the critic additionally sees reward bookkeeping and the torque mode |
| Export target | ONNX + metadata for the team's skill server; on-robot inference has to fit the 20 ms control tick |

<h2 id="simulation">Simulation and domain randomisation</h2>

Before training, I measured which randomisation factors actually hurt an existing kick policy (32 kicks per factor,
each factor alone):

- **Perception** (camera model + outages) was by far the most damaging: falls 15/32, touch rate 0.50.
- Next were trunk mass / centre of mass (11/32 falls), encoder offsets (10/32) and ball properties (9/32).
- **Physics rate:** launch speed changed only 7 % between 200 and 800 Hz, so 200 Hz was kept.
- **Ball model:** Isaac's per-step ball damping let the ball roll ~22 % too far compared with the rolling law; the
  MuJoCo ball model matched it within 2 % (restitution 0.45). This is why MuJoCo is the judge.

| Group | Range (per env or per episode) |
|---|---|
| Ground / foot friction | 0.4–1.3 / 0.6–1.2 |
| Ball radius / mass | 0.093–0.105 m / 0.28–0.40 kg |
| Ball rolling resistance | 0.4–1.2, later narrowed to 0.45–0.85 around the field fit 0.64 (see changelog) |
| Trunk mass / CoM | ±2 kg / ±2.5 cm |
| Link inertia, joint friction, armature | ±15 %, ±25 %, ±20 % |
| Encoder offsets, Kp/Kd scaling | ±0.02 rad, ±10 % |
| Actuator delay | 10–40 ms |
| Perception | 25 Hz camera, ~100 ms latency, field of view, head pose, dropouts including impact bursts, close-range noise |
| Pushes | 20–60 N for 0.1 s on the trunk, before and after the touch |
| Torque limits | per env: 75 % deploy limits, 25 % motor-peak curve, matching the benchmark rows |

| A7a / A7b | Firmware tracker / residual RL on top of it | the residual cut MuJoCo falls from 450 to 56 of 450 |

**Direction benchmark (450 paired MuJoCo scenarios, 8 physics rows).** The learned arms touched the ball 93–95 % of the
time, but the median direction error was 23–28° and the same at every commanded direction: random scatter, not a bias
that a correction could remove. Outcome-guided sampling of the diffusion policy did not reduce it either. Precision,
not contact, was the open problem, which is what the goal task measures directly.

<h2 id="benchmark">Goal task and benchmark</h2>

- **Goal:** the HSL middle-division goal from the team's field model, 2.6 m wide, 1.8 m high, 0.8 m deep, 10 cm posts; a goal counts when the
  whole ball is inside.
- **Shots:** ball-to-goal 1.5–4.5 m, up to ±50° off the goal normal, goal within ±45° of the robot's heading, ball
  placed where the team's walking behaviour leaves it.
- **Benchmark:** 5 000 seeded shots, identical for every policy, in MuJoCo, across deploy and peak torque rows. Quick
  screens (1 000 close + 1 000 far shots) every 250 iterations; decisions only on full validations, which repeat
  within about ±1 point.
- **Clean goal:** the first contact is a foot, there is no re-touch, and the ball goes in.

**A reward hack, found by the benchmark.** The first goal reward paid for any contact. Within 1 500 iterations A1
learned to shove close balls with its shin: Isaac reported 99 % touches, but in MuJoCo 11 % of shots had no foot
contact and clean goals halved (42 → 22 %). Gating every goal reward on a clean foot contact fixed it.

**Why far shots missed (A1 goal-trained, 3.75–4.5 m):** 42 % wide, 18 % on line but short. Launch speed was about
3 m/s at every distance, yet far shots on target score 17 % below 2.5 m/s and 96 % above 4 m/s. Slow kicks were also
less accurate (median aim error 21.6° vs 8.6°).

<h2 id="reward">Goal reward v2</h2>

Episode-scale terms, multiplied by the task weight in the AMP task/style mix:

| Term | Definition |
|---|---|
| Distance factor D | 1 + 0.5 · clip((d − 1.5)/3, 0, 1): far shots are worth up to 1.5× |
| Eligibility E | first contact is a foot, no re-touch, plausible launch, contact ≤ 120 ms |
| `goal_scored` | 20 · D · E |
| `goal_aim` | graded lateral miss on the goal line at launch, × D · E (weight later 6 → 10) |
| `launch_speed` | once per kick, ∝ on-target horizontal launch speed, × D · E (weight later 1 → 0.25 per m/s) |
| `quality` | one-sided: penalises launching slower than commanded, not faster |
| Revocation | a re-touch or a contact longer than 120 ms takes back all goal rewards paid so far |
| Fall | −20 minus the goal rewards already paid, so falling after a goal never pays |
| Episode | fixed 7 s after the first touch, so there is no incentive to keep the ball rolling |

<h2 id="changelog">Training changelog</h2>

Every step started from the best checkpoint of the previous one and changed one thing. Far = 3.75–4.5 m goal rate
on the full validation.

| Step | Change | Far goals |
|---|---|---|
| Start | A1 goal-trained | 39.5 % |
| 1 | Goal reward v2 | ~56 % |
| 2 | Longer credit assignment: γ 0.997, λ 0.99, 64-step rollouts (the set-up step happens ~0.5 s before the kick is paid) | ~59 % |
| 3 | Ball-rolling randomisation narrowed from 0.4–1.2 to 0.45–0.85: at 1.2 many far shots were physically unreachable, so training had pushed power over aim | ~65 % |
| 4 | Set-up factor: a first touch before 0.3 s pays 0.3× (rushed first touches 15 % → 2 % of far shots) | ~67 % |
| 5 | Ten more past ball detections (300 ms instead of 80 ms) | **73.4 %** |

Lines that did not beat the best, each tested on full validation:

| Change | Far goals |
|---|---|
| Training without the AMP style term (tested at step 1) | 53.9 %, no effect |
| Oversampling shots where the ball is unseen just before contact | 65.6 % |
| Lower KL target / learning rate | 68.9–70.1 % |
| Reach reward instead of quality | 69.8 % |
| Quality + reach | 72.3 % |
| Checkpoint weight averaging | 73.9 % (tie) |
| Hand-built ball filter as extra inputs | 73.1 → 67.5 % |
| Lower action noise (0.25 → 0.20) | 71.8 % far, but the best close rate: 92.2 % |
| Filtered ball estimate instead of the raw one | 73.0 % (tie) |

Plain extra iterations past a peak drifted down by 2–8 points, which is why every line restarts from the best.

<h2 id="next">Next steps</h2>

1. **A learned ball estimator** (rollouts of the best policy → a small MLP/GRU trained by supervised learning):
   the camera analysis puts the ceiling at up to ~17 far points.
2. **The left foot:** oversample left-foot situations; up to ~5 far points if left-foot kicks scored like right-foot
   ones.
3. **Foot-contact randomisation** (box vs mesh collider, friction, contact stiffness) for transfer to the real foot.
4. A one-time run on the locked test split for the final number, a turf measurement of rolling resistance, and then
   hardware tests on the K1.
